# 模式 · 多渠道适配器的维护与演进

> 从多渠道订单/支付对接实践提炼，是「多渠道对接的抽象层」的续集。
> 上一模式解决「抽象层怎么建」，本篇解决「适配器多了以后怎么养」——抽象层建立后的长期维护问题，比建立本身更消耗精力。

---

## 问题

抽象层建好后，适配器数量会持续增长（新渠道、新能力、新版本）。三年后你面对的不再是「N 个适配器」，而是：

1. **版本漂移**：渠道 API 升级了，适配器还停在旧版本；渠道侧静默兼容期一过，线上开始出怪问题
2. **僵尸适配器**：某个渠道已经不接入/不再调用，但适配器还留在仓库里，占用维护注意力和构建时间
3. **能力不齐**：各适配器支持的能力参差（渠道 A 支持全部能力，渠道 B 只实现了一半），核心流程无法区分「该有但没有」和「本来就没有」
4. **不敢动**：适配器与渠道强耦合，改动风险高，测试又依赖真实渠道（沙箱不稳定），于是「没人敢动」→ 越不动越陈旧

抽象层解决的是「加渠道的成本」，维护层解决的是「适配器长期存活的质量」。

---

## 结构

适配器生命周期管理，四个状态：

```
接入（onboarding）→ 在役（active）→ 待退役（sunset）→ 已退役（retired）
```

每个适配器必须在仓库里有**单一事实源**登记：状态、支持能力、渠道 API 版本、依赖的沙箱、负责人。

---

## 四个设计要点

### 1. 能力清单要显式声明，不能靠代码里有没有实现来判断

每个适配器声明「支持哪些能力」——用显式的能力清单，而不是靠读代码数方法。

```
适配器 X：
  支持：拉单 ✓ 发货 ✓ 退款 ✓ 查物流 ✗
  渠道 API 版本：v2（v1 兼容期至 2026-Q3）
```

能力清单的价值：核心流程拿到适配器时，能区分「该有但没有（bug）」和「本来就没有（设计如此）」——这是排障时最常被混淆的一对。

### 2. 渠道版本升级要有「联动检查清单」

渠道侧升级 API 时，不是改完适配器就完事，而是过一遍联动清单：

- 适配器版本号 + 渠道兼容期登记
- 状态映射表是否需要新增/调整
- 幂等键语义是否变化
- 沙箱/测试用例是否需要同步升级
- 下游依赖该适配器的流程是否需要回归

**关键**：渠道升级是高频事件（尤其支付类渠道），但没有联动清单时，适配器会「带病运行」——旧版本往往还能跑（兼容期），但兼容期一过就是线上事故。

### 3. 适配器测试要分「契约测试」和「真实联调」

依赖真实渠道的测试天生不稳定（沙箱波动、限流、环境差异）。把测试分成两层：

- **契约测试**：用录制的渠道报文样本，验证「报文 → 内部模型」映射正确性。不依赖真实渠道，可随时跑，是回归主力
- **真实联调**：只在版本升级、接入新渠道时跑，验证沙箱真实行为

契约测试是适配器「敢改」的前提——没有它，改动只能靠胆量。

### 4. 僵尸适配器要有「退役机制」

适配器退役不是删代码那么简单，要过流程：

- 确认无流量（查调用日志/指标，而不是问人「还在用吗」）
- 标记 sunset 状态 + 保留期（给依赖方迁移窗口）
- 保留期过后才 retire，从构建和登记表中移除

**关键判断**：退役动作必须基于「流量证据」，不是「记忆」。三年没动过的适配器可能还在被某个低频流程调用，删了就出事故。

---

## 检验维护是否健康的硬指标

> **适配器仓库里，有没有人说得清「每个适配器当前是什么状态、支持哪些能力、渠道版本是什么」？**

- 有人说得清（有登记表且是单一事实源）→ 维护健康
- 要翻代码才能说清 → 登记表缺位，该补
- 谁也说不清 → 僵尸化已经开始，先止血（至少把状态登记补起来）

另一个硬指标：

> **渠道 API 升级后，适配器在兼容期内完成升级的比例。**

兼容期是渠道给的安全窗口。每次都拖到窗口末尾甚至过期，说明适配器维护没有被当作「有节奏的常规工作」，而是「出事才处理」。

---

## 什么时候不需要这套维护机制

- 适配器数量少（≤3）且渠道稳定不升级：写个登记表都多余，直接维护
- 渠道对接是一次性的（接入后永不再升级）：维护成本低于机制成本
- 团队没有「长期养」的意愿：机制要人执行，没人执行时机制本身也是僵尸

---

## 一句话总结

> 抽象层决定适配器能不能加得动，维护机制决定适配器能不能活得久。渠道升级是高频事件、僵尸适配器是慢性病——把适配器的状态、能力、版本变成显式登记，把渠道升级变成联动检查，测试以契约为主，退役认流量证据，适配器就能长期健康，而不是越来越不敢动。
