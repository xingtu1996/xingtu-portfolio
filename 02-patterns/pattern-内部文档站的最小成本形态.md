# 模式 · 内部文档站的最小成本形态（docs-as-code）

> 从团队内部文档站的搭建实践提炼。
> 场景：团队知识散在聊天记录、个人笔记、共享盘，没有人维护；想要一个「大家会看、愿意更新」的内部知识库，但不想为此上重型文档系统。

---

## 问题

内部知识库最大的成本不是搭建，是**维护意愿**。

重型方案（wiki 平台 / 文档 SaaS）往往死于三个原因：

1. **更新成本高**：打开网页 → 新建页面 → 填表单 → 分类归档，操作链长，工程师不愿意为一次「顺手记录」走完
2. **与代码脱节**：文档系统是另一个世界，改代码的人不会记得去同步文档
3. **权限与接入复杂**：组织账户体系、SSO、审批链，搭起来就是半个月

结果：花大力气搭的系统，三个月后变成另一个「没人维护的共享盘」。

---

## 结构

**docs-as-code：文档源文件进仓库，静态托管，自动构建。**

```
markdown 源文件（与代码同仓或独立文档仓）
        ↓ 提交即触发
自动构建（CI 流水线）
        ↓
静态站点托管（Pages 类能力，零服务器）
```

核心原则：**文档是代码仓库的一部分，更新文档 = 一次提交。**

---

## 三个设计要点

### 1. 源文件必须能本地编辑、本地预览

工程师对文档的接受度，取决于「能不能像写代码一样写文档」：

- markdown 源文件，不是网页编辑器
- 本地可预览（本地起一个静态站点预览）
- 提交走 git 流程（评审、历史、回滚天然继承）

### 2. 目录结构即导航

文档站的导航 = 仓库的目录结构。**目录按主题组织，不按时间、不按作者**：

```
docs/
├── onboarding/      # 新人上手
├── architecture/    # 架构与设计
├── operations/      # 运维手册
└── playbook/        # 问题处理手册（排查路径）
```

目录即导航的好处：新内容落位时就要想「它属于哪个主题」——这个动作本身就是整理。时间轴导航（博客式）不适合内部知识库，因为知识是按主题被检索的，不是按日期被翻阅的。

### 3. 检索要原生可用

内部文档站能不能活，看「找得到」：构建产物要自带全文检索（Pages 类静态站也有轻量检索方案），并且**搜索结果直接跳转到对应源文件**——读者看到文档过时，能一键跳到源文件提 MR，而不是只能在网页上干瞪眼。

---

## 检验形态是否成立的硬指标

> **更新一条文档的成本，应该约等于一次代码提交。**

- 想在文档里加一段话 → 改 markdown → 提交 → 自动上线
- 不需要登录文档后台、不需要走文档系统特有的权限申请
- 文档过时 → 读者点开源文件 → 提一个改动的 MR，几秒钟完成

如果更新文档还需要「打开另一个系统」，这个形态就不成立，会退回「没人维护」。

---

## 什么时候不需要这个形态

- **个人笔记**：不需要多人协作和检索，本地文件即可
- **正式对外文档**：需要精细权限、审阅流程、对外品牌，静态站不够
- **团队完全没有更新意愿**：任何形态都救不了「没人写」——先解决激励，再谈工具

---

## 一句话总结

> 内部文档站能不能活，取决于「顺手记一笔」的成本。docs-as-code 把成本压到一次提交，同时让文档和代码共用同一套版本、评审、回滚纪律——文档不是代码的附属品，它就该是仓库的一部分。
