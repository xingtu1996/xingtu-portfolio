# 模式 · 多渠道对接的抽象层

> 从零售 OMS 的全渠道对接实践提炼（累计对接八家以上主流电商平台）。
> 场景：内部一套订单模型，外部 N 个渠道，每个渠道的 API、语义、状态机都不一样。

---

## 问题

渠道对接最容易被低估的一点是：**看起来是接口适配问题，实际上是语义对齐问题。**

接口差异是显式的——字段名不同、调用方式不同，写个适配器就完了。

语义差异是隐式的——同一个"已发货"，在渠道 A 意味着"物流单号已生成"，在渠道 B 意味着"揽收成功"，在渠道 C 可能包含"部分发货"。这种差异不会报错，只会让下游逻辑在个别渠道上行为诡异。

前两个渠道通常写得很快，问题从第三个开始：每次加渠道，都要在核心流程里加特判。加到最后，核心流程变成一堆 `if (channel == X)`。

---

## 结构

三层分工：

```
渠道能力接口层     定义"我们需要什么能力"（拉单 / 发货 / 退款 / 查物流 ...）
       ↑
渠道适配器层       每个渠道一个实现，把渠道 API 翻译成能力接口
       ↑
渠道配置层         渠道级参数：调用频率、超时、重试、幂等键、字段映射
```

**关键约束**：核心流程只依赖"渠道能力接口"，不允许出现任何渠道判断。

这条约束听起来理所当然，实践中最容易被破坏——因为"就这一次特殊"的理由永远存在。破一次，就会有第二次。

---

## 三个设计要点

### 1. 状态映射必须显式，不能靠约定

每个渠道的状态机单独定义，通过**显式映射表**转到内部状态。

```
渠道A: WAIT_SELLER_SEND_GOODS → 内部: 待发货
渠道B: PAID                   → 内部: 待发货
渠道C: READY_TO_SHIP          → 内部: 待发货
```

映射表是配置，不是代码。新增渠道加一张表，不改核心逻辑。

**为什么必须显式**：隐式约定会在人员更替时丢失。半年后没人记得渠道 B 的 `PAID` 为什么映射到"待发货"而不是"已支付"，于是没人敢动它。

### 2. 幂等键的选择决定重试是否安全

外部渠道会重复推送（网络重试、消息重发）。幂等键选错，要么漏单，要么重复单。

规则：**用渠道侧的原始单据标识做幂等键，而不是用内部生成的 ID**，也不要用订单金额 + 时间这类可碰撞的组合。

同时保留渠道原始报文——对账和排查时，原始报文是唯一可信的东西，转换后的内部模型已经丢信息了。

### 3. 单渠道故障必须能隔离

一个渠道的 API 挂了，不能拖垮其他渠道的拉单。

做法是**每个渠道独立的任务队列 + 独立的失败退避**，而不是一个统一的定时任务遍历所有渠道。后者会让一个慢渠道拖慢全部。

---

## 检验抽象是否成立的硬指标

> **接入第 N 个渠道的成本，应该低于接入第 N-1 个。**

如果成本持平，说明你只是写了 N 个适配器，抽象层没有沉淀。
如果成本上升，说明核心流程里已经混入了渠道特判，抽象正在腐化。

**怎么测**：加新渠道时统计"修改了多少个已有文件"。

- 只加新文件（适配器 + 映射表 + 配置）→ 抽象成立
- 需要改核心流程 → 抽象已经破了，该重构了

这个指标比任何设计评审都诚实。

---

## 什么时候不需要这层抽象

渠道数量少于三个，且短期内不会增加时，直接写两套对接代码比建抽象层更快。

抽象层的价值随渠道数量非线性增长——三个渠道是分水岭。在此之前，抽象层的成本大于收益。

---

## 一句话总结

> 多渠道对接的难点从来不是接口适配，而是语义对齐。判断抽象是否成功的唯一硬指标：第 N 个渠道是不是比第 N-1 个更容易接。
