# ADR-005 · 跨系统大版本升级：双轨并行 + 带 TTL 的开关表

```
编号：ADR-005
领域：遗留系统升级 / 跨系统接口迁移
决策时间：2026
我的角色：一线工程化实践者，升级实施主导
状态：已落地验证
```

---

## 背景

核心链路接口要跨大版本升级：老实现（多年演化、牵一发动全身）换成新实现（目标架构），但无法「一夜全切」——原因有三：

1. **依赖方众多**：核心链路被大量上游调用，逐个确认兼容性需要时间
2. **回归成本高**：全量切换后如果出问题，回滚代价大，且「切换失败」和「新实现有 bug」难以区分
3. **灰度诉求**：业务方希望按场景分批验证，而不是一刀切

---

## 选项

### 选项 A：一刀切切换

选定时间点，全部流量切到新实现。

- 优点：最简单，无并行成本
- 缺点：回滚是整体回滚，失败影响面大
- 缺点：没有灰度窗口，问题只能在上线后暴露

### 选项 B：双轨并行 + 无 TTL 的开关表

新旧实现同时在线，用开关表按场景/调用方切换；开关写入后长期保留。

- 优点：可逐场景灰度，风险可控
- 缺点：开关是「永久状态」——切换完成没人清理，开关表残留大量历史开关
- 缺点：残留开关会成为排障干扰项：排障时看到一个开关，得先判断「这个开关还生效吗？是谁开的？该不该动？」

### 选项 C：双轨并行 + 带 TTL 的开关表

在 B 的基础上，每个开关带过期时间（TTL），到期自动失效并进入清理流程。

- 优点：保留逐场景灰度的全部优点
- 优点：开关是「临时状态」——过期自动失效，残留被结构化清理
- 缺点：需要设计开关的 TTL 约定（多长合适？谁来续期？）

---

## 决策

**选 C：双轨并行 + 带 TTL 的开关表。**

决定性理由是**开关的语义从「永久配置」变成「临时灰度指令」**：

> 升级期的开关是过渡工具，不是永久配置。没有 TTL 的开关，会把一次升级的临时状态，永久留在生产配置里。

配套设计：

1. **开关粒度按场景/调用方划分**，不按「老 vs 新」全局二分——这样灰度顺序可控，出问题时影响面可枚举
2. **TTL 约定**：默认短周期，到期前可续期；续期必须带理由（证明「还没切完」而不是「忘了切」）
3. **到期后进入清理流程**：自动失效 + 日志留痕，防止「开关还在但没人知道它为什么在」
4. **双轨的入口保持统一**：调用方无感知，切换逻辑收敛在开关层

---

## 当时没看到的

**开关表本身会成为第二个遗留系统。**

第一版设计里，开关是「加上就不管」的。结果切换完成后，开关表里躺着几十个历史开关，没人说得清哪些还生效。排障时看到任何一个开关，都要花时间判断「这是不是这次问题的原因」——**排障成本被残留状态拉高了**。

**TTL 不是技术细节，是语义约定。**

加 TTL 表面上只是「多一个字段」，实际是把开关从「配置」重新定义为「指令」：指令天然有生命周期，配置没有。这个语义变化决定了后续所有处理逻辑（续期、告警、清理）的形态。

**另一个没料到的：双轨并行的时间不是按技术估算的，是按业务验证节奏定的。**

技术侧「切换」只需要一天，但「让每个场景都验证完」可能需要数周。排期时如果只估技术工量，双轨期会被严重低估——双轨不是技术状态，是业务灰度状态。

## 可复用条件

**适用**：

- 核心链路接口/服务跨大版本升级，无法全量切换
- 存在明确的场景/调用方可枚举
- 需要逐批灰度验证，且失败后要能快速缩小影响面

**不适用**：

- 无场景可枚举的纯内部重构（双轨收益低，直接切即可）
- 升级窗口内没有真实流量可灰度（双轨形同虚设）

**一个判断口诀**：

> 任何「临时状态」都要有生命周期。加了 TTL 它才是临时状态，没有 TTL 它就成了永久配置——而永久配置是最容易被遗忘的排障干扰项。

**另一个更通用的教训**：

> 升级类项目的排期，技术切换只是其中一小段，业务验证节奏才是大头。估工量时问「每个场景要验证多久」，而不是「代码要改多久」。
