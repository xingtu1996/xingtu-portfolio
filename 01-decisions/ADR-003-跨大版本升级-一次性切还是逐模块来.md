# ADR-003 · 跨大版本升级：一次性切，还是逐模块来

```
编号：ADR-003
领域：遗留系统演进 / 技术债
决策时间：2025 - 2026
我的角色：技术经理，项目统筹
状态：已落地
```

---

## 背景

一套跑了六七年、由数十个微服务组成的零售中台。这一次不是加功能，是**还债 + 合规**：

- 底层框架落后多个大版本，官方早已停止维护
- 运行时版本落后两个 LTS，新依赖装不上，老依赖有已知风险
- 有一批已知漏洞需要修复，其中部分是框架层面导致的
- 系统每天在跑真实交易，**没有停机窗口**

约束：

- **业务约束**：不能停服；大促期间冻结变更
- **技术约束**：服务间通过注册中心与声明式调用耦合，升级不是单个服务的事
- **组织约束**：团队同时并行其他项目，没有整块时间
- **验收约束**：升级本身不产生可见业务价值，甲方看不到"你做了什么"

最后一条是最难受的。做新功能，做完有东西可演示；做升级，做成了是"什么都没坏"，做砸了是"你把系统搞坏了"。

---

## 选项

### 选项 A：立项大版本升级，一次性切换

拉一个专项，全员投入，把所有服务统一升到目标版本，一次性切。

- 优点：技术债一次性还清，没有中间态
- 优点：不需要维护双版本兼容层
- 缺点：周期长，中间没有任何可交付物
- 缺点：风险集中。切的时候出问题，回滚是全体回滚
- 缺点：与并行项目抢人，实际排期会一拖再拖

### 选项 B：只升安全补丁，不大动框架

哪里有问题修哪里，不碰大版本。

- 优点：改动最小，风险最低
- 缺点：治标。老框架的坑会在下一次需求里再踩一遍
- 缺点：新依赖依然装不上，技术栈继续僵化
- 缺点：过半年又要面对同样的问题，而且更严重

### 选项 C：分层推进，按依赖顺序逐模块升级

先升底座（注册中心、配置中心、公共库），再按依赖层级由下往上逐服务升级，每个服务独立上线、独立回滚。

- 优点：每步都有可交付物，风险分散
- 优点：单个服务出问题只回滚单个服务
- 优点：可以和业务需求穿插排期，不抢人
- 缺点：需要长期维护"部分已升级"的中间态，兼容层复杂度上升
- 缺点：总周期比 A 更长
- 缺点：对依赖顺序的梳理要求高，梳理错了要返工

---

## 决策

选 **C：分层推进**。

决定性理由是**验收可行性**，不是技术风险：

> 一次性升级的项目，在整个周期里没有任何可展示的成果。这类项目在资源争夺中最先被砍。切成逐模块之后，每升完一层就有一个明确的交付节点。

这个判断听起来很"政治"，但它决定了项目能不能活到做完。技术债务类项目的死法通常不是技术失败，是**中途被叫停**——因为没有可见进展。

配套的三个做法：

1. **先画依赖拓扑，再排顺序**：不动手改代码，先把服务间调用关系理清楚。从"被依赖最多、依赖别人最少"的底座开始
2. **公共库先行，业务服务在后**：所有服务共用的基础组件必须先升，否则上层升完还要再升一遍
3. **每升一层留一个可回滚点**：不做"升到一半"的状态，每个服务要么完整升级，要么完整回滚

## 当时没看到的

**第一个教训：编译通过不等于升级完成，兼容问题在运行时才暴露。**

升级列表里有一类问题最阴——**序列化兼容**。服务 A 升级后，与未升级的服务 B 之间传递的对象结构没变，但底层序列化框架的行为变了，导致反序列化失败。编译期完全无感，联调才发现。

后来加了一条硬规矩：**任何跨服务边界的数据结构，升级前后必须做一次全链路序列化往返验证**。这条不在任何官方升级指南里，是踩出来的。

**第二个教训：配置文件是最大的隐藏工作量。**

代码里的 API 变更有编译器帮忙查。配置项的变更没有。我们低估了配置迁移的工量——老配置项废弃、改名、默认值变更，这些散落在几十个配置文件里，只能靠批量脚本加人工核对。

如果重来，我会在项目启动时就**把配置迁移单列成一个工作项并单独估工量**，而不是把它算在"改代码"里。

**第三个教训：兼容层要有明确的拆除时间。**

为了支持中间态，我们写了不少兼容代码。问题在于——**没有给兼容层设死线，它就永远在那**。升级完成后，这些代码变成了新的技术债，而且是最难清理的那种（没人确定还用不用）。

正确做法是：写兼容层时就约定拆除条件和时间点，写进代码注释和项目计划。

## 可复用条件

**适用分层推进**：

- 服务数量多、依赖复杂，无法一次性切换
- 没有停机窗口
- 团队并行其他项目，无法全员投入
- 升级本身没有可见业务价值，需要用节点证明进展

**不适用**：

- 服务数量少、依赖简单（一次性切更干净）
- 有充足停机窗口（大爆炸成本更低）
- 底层变更破坏性极强，无法做兼容层（此时必须一次性切）

**三个判断口诀**：

> 一、技术债项目的排期要按"可见节点"切，不按"技术完整性"切。没有中间交付物的项目会死在资源争夺里。

> 二、升级工量 = 代码改动 + 配置迁移 + 跨服务兼容验证。只估第一项，后面会翻倍。

> 三、任何为过渡而写的兼容代码，必须在写下时就约定拆除条件。没有死线的兼容层就是下一代技术债。
