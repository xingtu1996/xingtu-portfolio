# ADR-004 · 自动化管线与人工操作竞争写同一文件：先定位根因，再谈锁

```
编号：ADR-004
领域：CI/CD 配置治理 / 部署自动化
决策时间：2026
我的角色：一线工程化实践者，配置与部署协同
状态：已落地验证
```

---

## 背景

一套部署配置仓库里，存在两类写入者：

- **自动化管线**：CI 触发后按自己维护的「版本表」更新部署配置（镜像 tag 等）
- **人工 / AI 协助操作**：为某个专项需求手动设置特定 tag

出现了一个极其迷惑的现象：**改完、提交、推送，看起来都成功了，但过一会儿配置又被改回去了。** 第一次遇到时，我们花了很长时间排查 git 操作本身——怀疑是拉取合并冲突、分支覆盖、本地缓存之类的问题。

反复验证后发现：**git 操作没有问题，是自动化管线在每次 CI 触发时，用它的版本表覆盖了人工设置的值。**

根因链条：

```
人工设置新值 → CI 触发 → 自动化管线按自己维护的版本表重写同一文件 → 版本表过时（不认识新值）→ 部署被回滚到旧值
```

---

## 选项

### 选项 A：人工操作让位，遵守「管线唯一写入权」

既然自动化会覆盖，人工就不直接改文件，所有变更都走管线的版本表入口。

- 优点：写入者唯一，不再有竞争
- 缺点：专项需求往往就是要绕过管线默认逻辑（比如临时指定一个管线版本表里没有的值）；只靠管线入口可能根本表达不了这个需求
- 缺点：没有根治「版本表过时」——问题只是被绕开了

### 选项 B：同步更新自动化管线的版本表（治根因）

让管线认识新值：把人工设置的值登记进版本表，管线下一次触发就用新值而不是回滚。

- 优点：根因解决——版本表和数据源一致后，自动化不会再把配置改回去
- 缺点：版本表在 CI 侧维护，更新它需要找到正确的配置位置；跨团队时沟通成本高
- 缺点：每个专项值都要登记一次，长期靠人记不可持续

### 选项 C：对特定条目加锁定/白名单

给需要人工固化的配置项加「锁定」标记，管线跳过这些项。

- 优点：一劳永逸保护专项值
- 缺点：锁定机制本身要设计（锁在哪一层、谁能解锁、锁了之后管线告警怎么处理）
- 缺点：锁定条目多了，管线的「自动更新」承诺名存实亡

---

## 决策

**选 B（同步版本表）为主，A 为纪律底线，C 仅对极少数必须长期固化的条目启用。**

理由：

1. **B 是根因修复**——版本表过时是「慢变量」：它不会立刻暴露，但每次 CI 触发都在累积覆盖。修好版本表，自动化与人工作业从「竞争」变成「协同」。
2. **A 作为默认纪律**：日常变更一律走管线入口，人工直接改文件是例外而不是常态。这个纪律把竞争发生的频率降到最低。
3. **C 只在 B 无法表达需求时启用**（例如某个值只在本轮专项有效、不便进版本表），且必须带到期机制，防止锁定条目永久残留。

配套动作：

1. 定位版本表的维护位置（CI 侧配置），把「版本表过时」加入变更 SOP 的检查项
2. 对人工直改行为加日志/注释标记，让下一次覆盖发生时能快速定位是谁改的、为什么
3. 覆盖发生即告警——不等到部署出问题才发现

## 当时没看到的

**第一反应「以为是 git 问题」是最大的时间黑洞。**

症状（改动被回滚）和 git 冲突症状高度相似，但根因完全不同。我们在 git 侧排查了很久，才意识到要去查「除了我，还有谁在写这个文件」。

**另一个没料到的：版本表是慢变量，会被当作「偶发」而忽略。**

第一次出现回滚时，直觉是「哪次操作没推上去」。只有当同一个文件被连续覆盖多次、且每次都被改回同一个旧值时，才意识到这不是偶发，而是一个有规律的自动化行为。

**还有一层：这本质上是「谁有权写」的治理问题，不是技术问题。**

技术上一分钟就能「再改一次」，但如果不同步版本表，改多少次都会被覆盖。真正的解法是定清楚**所有权**：这个文件的权威来源是谁，人工变更怎么进入权威来源。

---

## 可复用条件

**适用**：

- 存在 CI/自动化定期改写配置文件（部署配置、路由表、特性开关文件）
- 人工偶尔需要设置自动化版本表里没有的值
- 出现「改了就回滚」且 git 操作本身无异常的怪异现象

**不适用**：

- 配置文件完全人工维护、无自动化写入（不存在竞争）
- 自动化只是读取不写入

**一个判断口诀**：

> 配置被「改回去」时，先别查 git——先问「除了我，还有谁在写这个文件」。写文件的人多于一个，问题就在所有权，不在操作。

**另一个通用教训**：

> 自动化管线的「自动更新」承诺建立在它自己的数据源（版本表/配置表）准确之上。数据源是慢变量，没人维护的数据源一定会过期，过期后自动化不是帮手，是回滚器。
